checked against an upstream published list, because corpus-texmex does not publish one — so on
their own they establish nothing. What actually validates these archives is `anka load`, which

`scripts/hdf5_to_fvecs.py`. Its `distance` attribute reads `angular`, and the vectors are **not**
pre-normalised — cosine has to normalise at insert time.

| | query | 10 000 × 100 | 3.8 MiB | 4.38 ms |
| | groundtruth | 10 000 × 100 | 3.8 MiB | 3.44 ms |

Load times are page-cache-warm — the files had just been downloaded and extracted. They are
recorded as a sanity check on the reader, not as I/O measurements; cold-cache figures come with
the mmap comparison in phase 3.

### Peak resident set size

| Dataset | Data held live | Peak RSS | Overhead |
|---|---|---|---|
| siftsmall | 5.0 MiB | 8.9 MiB | 3.9 MiB |
| SIFT1M | 497.0 MiB | 501.1 MiB | 4.1 MiB |
| GloVe-100 | 459.1 MiB | 463.3 MiB | 4.2 MiB |

"Data held live" is base + query + ground truth, all three resident simultaneously.

The overhead stays flat at roughly 4 MiB regardless of dataset size, and that is the phase 0
result worth keeping: the readers stream record by record into the destination buffer instead of
reading the file into memory and decoding afterwards. A slurping reader would peak near 1 GiB on
SIFT1M — the 516 MiB file plus the 512 MiB of floats decoded out of it.

### Robustness

Malformed input returns an error and never panics. Covered by tests:

| Case | Result |
|---|---|
| Empty file | `Empty` |
| File shorter than the 4-byte dimension header | `Truncated { record: 0 }` |
| File truncated mid-stream | `Ragged` with the record size and dimension |
| A record whose declared dimension disagrees with the first | `InconsistentDim` with the record index |
| Dimension header of 0 | `ZeroDim` |
| Dimension header of `u32::MAX` | `DimTooLarge` — no multi-gigabyte allocation attempted |
| NaN or infinity in the data | `NonFinite` with the vector and component index |
| Mapping smaller than its declared shape | `MappingTooSmall` |
| Misaligned mapping offset | `MisalignedOffset` |
| Unknown metric tag in a header | `None`, not a silently wrong metric |

|---|---|
| 1M index write → reload, results bit-identical | *pending* |
| WAL replay path, results bit-identical | *pending* |
| mmap load time vs full read | *pending* |
| `kill -9` during WAL write, `fsync=always` | *pending* |
| `kill -9` during snapshot write | *pending* |
| Torn WAL: truncated `len` / truncated payload / bad CRC / `seq` gap | *pending* |
| Corrupt snapshot: bad magic / unknown version / bad header CRC | *pending* |

**What the crash test proves:** recovery survives a torn log and an interrupted snapshot, and no
record acknowledged under `fsync=always` is lost to a process kill.
**What it does not prove:** power-loss durability. `kill -9` leaves the page cache intact, so it
cannot demonstrate that. No such claim is made.
